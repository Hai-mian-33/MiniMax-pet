# MiniMax Pet — MiniMax Code 桌面版任务进度桌宠

把 MiniMax 官方主视觉那只蓝色小团子放在桌面上，**实时反映 MiniMax Code 里正在跑的任务**：
提交任务 → 思考中；调用工具 → 执行中并显示工具名与步数；工具发出去了但迟迟没回结果 →
橙色「等你确认」；回合收尾 → 绿色 ✓ 与用时。多个会话各自独立成卡片，互不覆盖。

**这个文件夹是完全自包含的**，可以整体移动到任何位置：所有路径都由
`os.path.dirname(os.path.abspath(__file__))` 推出来，不含任何写死的绝对路径，
启动脚本一律用 `%~dp0`。删掉原始开发目录 `Desktop\MiniMax-pet` 不会影响它。

唯一的外部引用有两个，都是只读/可选的：

| 外部位置 | 性质 |
|---|---|
| `~\.minimax\v2\sessions\...` | **只读**，读会话转录用 |
| `%APPDATA%\...\Startup\MiniMaxPet.vbs` | 可选登录待命（拉起哨兵），`remove_autostart.bat` 可撤销 |

> 唯一真正的外部**依赖**是 `pythonw.exe`（Startup 时的 PATH 未必带 Python，所以
> VBS 里写死了绝对路径）和 PyQt5。`python autostart.py status` 会体检这两项。

## 它是怎么知道任务进度的

**只读监听会话转录文件**，不装钩子、不改任何配置：

```
~/.minimax/v2/sessions/<年>/<月>/<日>/<会话>/messages.jsonl
```

MiniMax Code 每轮对话都会实时追加到这个文件，桌宠按字节偏移**增量 tail**（700ms 一轮，
新会话目录每 12s 重扫一次），从三类消息推导状态：

| 转录里的信号 | 桌宠表现 |
|---|---|
| 出现新的 `role: user`（且带真实提问） | 状态回到**思考中**，卡片标题换成你这次问的内容 |
| `role: assistant` 里出现 `toolCall` | **执行中**，状态条显示工具名，卡片累计步数 |
| 工具已发出但超过 4s 没有对应 `toolResult` | **等你确认**（橙色脉冲感叹号 + 托盘通知） |
| `role: toolResult` 且 `isError: true` | 记一次失败，卡片左侧状态条转红 |
| `role: assistant` 出了纯文本、且没有待回收的工具调用 | **完成**（绿色 ✓ + 步数/用时），常驻到你点开查看 |

项目名来自同目录 `llm-call.json` 里 systemPrompt 的 `Primary working directory`（按
mtime+size 缓存，不会每次重解析）。

**关于标题准确性**（踩过的坑，已处理）：

- user 消息里除了你的提问，还塞着 `<system-reminder>` 环境上下文。程序用消息自带的
  `canonicalTextRange` 精确切出真实提问；如果这条 user 消息的该区间是**空的**（纯系统
  注入），就判定它不是新任务，**保持当前状态不变**——不会把工具 schema 当成任务标题，
  也不会把步数和错误数错误归零。
- 会话被**压缩**过时（转录首条是 `compactionSummary`，原始提问已被替换成回顾），
  标题取自回顾正文的第一句有内容的话，而不是 `## Goal` 这种光秃秃的分节名。

**开销**：只读新增字节，单轮亚毫秒级；首次全量读取单个转录上限 12MB，只关注最近 12 小时的会话。

## 交互

| 操作 | 效果 |
|---|---|
| **单击团子** | **把 MiniMax Code 窗口带到前台**。窗口开着就只置前，最小化了就还原；**已经被你关闭、但后台进程还赖着不走**时不会复活那具僵尸，而是结束残留进程重新拉一个（见下面「召唤卡死」；后台有任务在跑时则不结束进程，只还原窗口）。任务**还在跑**时：只跳转，卡片和团子脸都不动；任务**已结束**时：顺手把这个任务收掉，团子立刻切到下一个或回到「待命」 |

| `Ctrl+Alt+M` | 全局呼出 / 隐藏 |
| 卡片折叠 | **默认只显示 1 张**，其余收进底部的 `▼ 还有 N 个任务`；点它完全展开，展开态底部变成 `▲ 收起` |
| 点过的任务 | 任务**结束后**点一下跳转会收起它，此后它**既不出现在折叠的那一张里，也不出现在展开列表里**，直到有新任务重新冒出来 |
| 右键团子 | 显示/隐藏桌宠（手动）· 显示/隐藏卡片 · **展开/折叠全部任务** · **跟随 MiniMax Code 开关**（附「跟随依据」子菜单）· **MiniMax 完全退出时一并退出** · 跳转到 MiniMax Code · 演示一轮 · 重置位置 · **退出桌宠（不再自动拉起）** |

> **关于「跳转到对应任务界面」**：目前只能跳到 **MiniMax Code 窗口级**，做不到跳到某个具体
> 会话界面。原因是 MiniMax Code 没有开放会话路由的深链协议：注册表里的 `minimax-cn://`
> 只是 LLM provider 的标识符，不是页面路由；本地也没有可用的运行时端口或会话切换 API。
> 这和你说的「实验不了也没关系」一致。窗口级跳转是**实测可用**的：枚举到
> `MiniMax Code.exe` 的主窗口后 `SW_RESTORE` + `AttachThreadInput` + `SetForegroundWindow`，
> 实测约 120ms 置前，`GetForegroundWindow()` 校验一致。

### 召唤卡死：为什么以前会弹出「界面完整但点不动」的窗口

用户反馈过这么一条路径：**点关闭键关掉 MiniMax Code（后台进程没死）→ 点团子召唤
→ 弹出一个完整渲染、但整个界面卡死的窗口，停在关闭前的样子。**

**第一版的诊断是错的，值得记下来。** 当时判断是「渲染进程死了、窗口僵死」，于是加了
`SendMessageTimeout(WM_NULL, SMTO_ABORTIFHUNG)` 探活 —— 结果用户再测，**照样卡**，
日志写的是：

```
召唤 MiniMax Code [focus] 1 个活窗口，直接置前
```

探活**通过了**。原因：`WM_NULL` 只能证明窗口所属线程还在泵消息，而 Chromium 只要消息泵
还在就会照答不误，**界面死没死它根本不知道**。所以「靠检测识别僵尸」这条路走不通。

真正的触发点跟「僵不僵」无关，就是一句：**用户点关闭把窗口收起来了，而后台进程还活着；
是我们主动 `ShowWindow(SW_SHOW)` 把一个已经被关闭的窗口放回屏幕上的。** 放回去的只有
那一帧像素 —— 界面看着完整，渲染进程却已经不在了。

所以改成**按窗口状态分流，而不是靠探活**：

| 窗口状态 | 判定 | 处置 |
|---|---|---|
| 开着 | 看得见、非最小化 | **只置前，一个 `ShowWindow` 都不发** |
| 最小化 | 看得见、`IsIconic` | `SW_RESTORE` + 置前（最小化时渲染进程一定还活着） |
| **已被关闭** | 看不见（含 DWM cloaked） | **绝不复活**：`WM_CLOSE` → 复核 → 结束残留进程树 → 拉全新实例 |

进程活着但一个窗口都没有（托盘驻留 / 刚被关干净）也走最后一条，只是没进程可清。

判定顺序也踩过坑：**先判「看不看得见」再判「最小没最小」**。反过来会出事 —— 一个被最小化
之后又隐藏的窗口 `IsIconic()` 仍然为真，会被误判成最小化，于是对它 `SW_RESTORE`，
又把关掉的窗口放回屏幕。凡是看不见的，一律算「已关闭」。

结束残留进程树有三道闸，任何一道不过就整棵树放弃：

- 该进程在**桌宠自己的祖先链**上（手工启动时 MiniMax Code 完全可能挂在桌宠上面，
  杀了等于连自己一起送走）；
- 该进程树里还有任何**开着 / 活着**的窗口；
- 保护的是**祖先闭包**而不只是后代 —— 活窗口常在渲染子进程里、残留窗口在它的父进程上，
  只保护后代的话杀父会顺手把活的带走。

还有一条人味儿的安全兜底：**后台还有任务在跑的时候（`watcher.count_active() > 0`）
绝不结束任何进程**，只老老实实还原窗口 —— 杀进程会把正在跑的任务一起杀掉。

「等新窗口冒头」时也只认**非 hidden** 的窗口，否则进程里那个关着的旧窗口会冒充成
新窗口，召唤会假成功。

兜底的 exe 路径不写死：先用 `QueryFullProcessImageNameW` 问活着的进程要
（跟着安装位置走），要不到再退回 `%LOCALAPPDATA%\Programs\MiniMax Code\`，
再不行用开始菜单的 `MiniMax Code.lnk`。

> 还有一个容易被忽略的点：这套流程最坏要十几秒（等体面退出 + 等新窗口冒头），
> 所以 `activate_app()` **只在子线程里调用**，结果用 `BRIDGE.activate_result` 搬回
> 主线程再改 UI。放主线程的话，桌宠自己会先冻住 —— 那才是字面意义上的界面卡死。

排查用的两个入口：

```bat
python probe_windows.py                  :: 56 项离屏探针，不碰真实 MiniMax Code
python minimax_pet.py --probe-activate   :: 打印召唤链路每一步（含每个窗口的状态）
curl http://127.0.0.1:8766/              ;; windows=N 个（开着 A / 最小化 B / 已关闭 C）
```

### 召唤链路上踩过的坑

- **靠检测识别 Chromium 僵尸窗口是不行的**，`WM_NULL` 探活会给出假的「活着」。
  正确姿势是按「用户是不是已经把这个窗口关掉了」分流，而不是问「它是不是还活着」。
- **`OpenProcess` / `QueryFullProcessImageNameW` / `TerminateProcess` 都在 kernel32，
  不在 user32。** 写错库的那一版里，`_bind_extra()` 用一个大 `try` 包住所有绑定，
  第一条失败就整块中断 —— 排在后面的 `CloseHandle` 签名**根本没绑上**，静默退回
  ctypes 默认的 c_int，64 位下句柄高位被截断，拿去 CloseHandle 关的就不是那个句柄了。
  现在改成**每条单独 try**，绑不上就往 `pet.log` 写一行 `绑定 XXX 失败`，一眼能看出来。
- **`ctypes.wintypes` 里没有 `WNDCLASS`**，只有 `WNDCLASSEXW`；写离屏探针要自己
  补结构体，而且 `WNDPROC` 回调对象必须**保住引用**，否则被 GC 之后窗口类直接失效。
- 探针里 `WNDPROC` 必须**转发 `DefWindowProc`**，自己 `return 1` 的话
  `ShowWindow(SW_MINIMIZE)` 不会被处理，`IsIconic` 永远为假。
- **打桩 `time.sleep` 会打到自己**：`P.time` 就是全局 `time` 模块，
  `P.time.sleep = lambda: time.sleep(0.005)` 是无限递归。得先把真 `sleep` 抓出来再用。

## 显隐：跟随 与 手动，怎么共存

你要求的其实是两件独立的事，它们分别由两个开关负责：

| | 跟随 MiniMax Code | 手动（Ctrl+Alt+M / 托盘 / 右键） |
|---|---|---|
| 负责 | 应用**打开 / 关闭**那一刻，桌宠自动出现 / 消失 | 你当下想看还是不想看 |
| 开关位置 | 右键 / 托盘的勾选项，会落盘 | `Ctrl+Alt+M` 或托盘左键 |
| 优先级 | 手动盖在跟随上面 | 优先 |

手动隐藏是一次**临时覆盖**：本次不打扰你，等 MiniMax Code 下次打开，跟随重新接管，
桌宠自己回来。手动显示则会立刻清掉这次覆盖，并按当前应用状态同步。

### 曾经踩的坑：手动操作会静默改掉跟随开关

用户反馈「桌宠怎么不显示了」，查下来 `pet_state.json` 里 `follow` 已经是 `false`。
原因是 `toggle_visible()` 里这一段：

```python
# 旧代码：手动唤出时把跟随悄悄关掉，还落了盘
if self.follow:
    self.follow = False
    self.state["follow"] = False
    save_state(self.state)
```

用户只是想让桌宠出来看一眼（或者用完顺手隐藏），**跟随开关从此就永久变成了关**，
而且没有任何提示。之后桌宠既不随应用显隐，用户也会以为「跟随坏了」。

现在手动开关只碰 `manual_hidden`，`follow` **只有用户自己点那个勾选项才会变**。

### 「关掉窗口」和「退出进程」是两件事，别混

用户反馈过：点关闭键之后后台进程还留着，**后台 agent 要继续跑，桌宠也该继续显示**。
但「显隐」到底跟进程还是跟窗口，需要分成两个口径，而且**跟哪个可以换**：

| 口径 | 含义 | 适合谁 |
|---|---|---|
| **按进程存活**（默认） | 进程还在就算「开着」，窗口关不关无所谓 | **后台 agent 要继续跑、桌宠也该继续显示** ← 你的习惯 |
| 按窗口显隐 | 非要有 visible / minimized 的窗口才算「开着」 | 想让「窗口关了 → 桌宠也跟着藏」 |

菜单里是「跟随 MiniMax Code 开关」+ 一个「跟随依据」子菜单，两个口径单选，会落盘在
`pet_state.json` 的 `follow_mode`（`process` / `window`）。

而**退出永远只看进程**（`app_running`）：窗口关了但后台还活着时，桌宠不该跟着自杀；
只有进程真没了，`exit_with_app` 才让它退。

探针里对这三条路径都有覆盖，特别是「窗口关（进程还在）→ 按进程模式继续显示 /
按窗口模式隐藏」这一对。

### 「关掉窗口」曾经被当成「应用关了」

早先显隐只跟 `app_running()`（进程在否）判，后来有一版改成了跟窗口，于是
「关掉窗口、后台继续跑」时桌宠莫名其妙藏了。现在按你的习惯定成**默认跟进程**，
并保留窗口口径作为可选项。

### 手动关闭之后怎么回来

「退出桌宠」会写一个暂停标记，哨兵尊重它。为了让**手动关闭**真的是关闭：

- 哨兵**不再**因为应用重新打开就自动清掉这个标记（以前会，于是「手动关闭」等于没关）；
- TTL 从 12 小时放宽到 **3 天**，纯粹作为「标记永久遗留」的兜底；
- 恢复入口都放在手够得到的地方，**双击 `MiniMaxPet.bat`** 就行（它内部就是 `--resume`）。
  桌宠退出后托盘也没了，托盘里加「重新启用」是没法点的，所以入口必须在外面。

> `MiniMaxPet.bat` 必须**只写 ASCII**。`cmd.exe` 按控制台代码页（这里是 936/GBK）读 bat，
> UTF-8 的中文注释会被解成乱码碎片，`cmd` 接着把碎片当命令执行——
> 实测中文 `rem` 行直接报 `'……' is not recognized as an internal or external command`。
> 文档写在 README 里，bat 里只留英文。

## 生命周期（先看这张表）

**桌宠与 MiniMax Code 同生共死。** 登录时起来的不是一个能看见的桌宠，而是一个
**什么都不显示的待命哨兵**。

| 事件 | 桌宠进程 | 桌宠窗口 |
|---|---|---|
| **Windows 登录** | 未启动。起来的只有 `pet_watcher.py` 哨兵 | 桌面上**什么都不出现** |
| **启动 MiniMax Code** | 哨兵用 pythonw 拉起 `minimax_pet.py --exit-with-app` | ✅ 自动出现 |
| **打开 MiniMax Code 窗口**（进程已在，窗口被关着） | 不用管 | ✅ 按「跟随依据」决定（默认按进程 → 显示） |
| **关掉 MiniMax Code 窗口，但后台进程还留着** | 留着不退（退出只跟**进程**） | ✅ **默认继续显示**（后台 agent 还在跑，桌宠就该在） |
| **完全关掉 MiniMax Code**（进程也没了） | ✅ **跟着退出**（连续两次 3 秒轮询没检测到就自杀） | 消失 |
| **再次启动 MiniMax Code** | 哨兵还在，再拉起一个新的 | ✅ 重新出现 |
| **桌宠意外死掉**（崩溃 / 被清理工具杀） | ✅ 哨兵 **10 秒内自动复活**（实测 ~10s） | ✅ 自动恢复 |
| **锁文件损坏，桌宠起不来** | ✅ 哨兵连抓 2 次空拉后**自动清掉损坏的锁**再拉（实测 ~15s） | ✅ 自动恢复 |
| **哨兵意外死掉** | ✅ 桌宠 **9 秒内把哨兵拉回来**（实测 ~4s） | 不受影响 |
| **手动隐藏**（Ctrl+Alt+M / 托盘 / 右键） | 不动 | 隐藏。**跟随开关和依据都不变**，下次打开 MiniMax Code 会自动回来 |
| **菜单 / 右键勾掉「跟随」** | 不动 | 立刻放出来，从此**不再随应用显隐**，只听手动开关 |
| **「退出桌宠（不再自动拉起）」** | 退出，并写暂停标记 | 消失。**只有你显式恢复它才会回来**（双击 `MiniMaxPet.bat` / `--resume` / 重新登录） |

> 手动与跟随是**两个正交维度**：跟随管「应用开/关那一刻的自动显隐」，手动管「你现在想不想看」。
> 手动操作**永远不会**改掉跟随开关——以前手动唤出桌宠会把 `follow` 静默改成 `false`
> 并落盘，用户只是想让它出来一下，从此就再也不跟随了，而且没有任何提示。见下面那一节。

```
Windows 登录
    │
    ├─ pet_watcher.py 启动 ── 无窗口 / 无托盘 / 不 import Qt
    │      每 1.5 秒探一次 MiniMax Code 进程，桌面上什么都不显示
    │
    ├─ MiniMax Code 打开 ──→ 用 pythonw 拉起 minimax_pet.py --exit-with-app
    │                            └─ 桌宠出现
    │
    ├─ 桌宠没了 ──→ 哨兵拉起来            ← 状态驱动，不是边沿触发
    ├─ 哨兵没了 ──→ 桌宠把哨兵拉起来      ← 互相看门
    │
    └─ MiniMax Code 关闭 ──→ 桌宠自己退出（哨兵继续待命，等下次）
```

| 方式 | 说明 |
|---|---|
| **同生共死** | **默认且推荐**。就是上面这套，不需要任何配置 |
| 随应用显隐 | 托盘取消勾选「MiniMax 退出时一并退出桌宠」→ 退回到「关应用只隐藏、进程留着」 |
| 手动开关 | 托盘左键 / `Ctrl+Alt+M` / 右键菜单。手动接管一次后「跟随」自动关掉 |
| **想彻底关掉** | 托盘右键「退出桌宠」。哨兵**不会**再拉它（写 `pet_paused.flag`），直到你重新打开一次 MiniMax Code，或跑 `python pet_watcher.py --unpause` |
| 关闭登录待命 | `remove_autostart.bat` 撤销，或 `python autostart.py off` |

### 为什么是「哨兵 + 桌宠」两个进程

要让桌宠**在 MiniMax Code 打开的那一刻**起来，必须有个东西一直在等那个时机。
而 MiniMax Code 没有开放「应用启动时执行外部命令」的接口——它的 `config.yaml` 里
根本没有 hooks 段，纯应用内逻辑够不到。

那就只剩两种做法：

| 方案 | 问题 |
|---|---|
| 桌宠登录就常驻，只管显隐 | 进程**无条件常驻**，一周不开应用也一直挂着；而且窗口会先显示再隐藏 |
| **哨兵常驻 + 桌宠按需起落** ← 采用 | 只有一个十几 MB 的空转进程，且它**完全不可见**；桌宠是真同生共死 |

哨兵进程常驻是有意为之的——它是唯一能在 MiniMax Code 下次启动时立刻反应的东西。
但它没有窗口、没有托盘图标（pythonw 无窗口），任务栏也看不到。

### 互相看门：为什么桌面不会再空掉

哨兵和桌宠**互相盯着对方**，任何一个掉线另一个都会把它拉回来。

```
        应用开着
            │
   ┌────────┴────────┐
   │                 │
 桌宠                哨兵
   │ ← 「你在吗？」   │ → 「你在吗？」
   │    没了就拉     │    没了就拉
```

**为什么非要有这个？** 因为最早的哨兵是**纯边沿触发**的：只在 MiniMax Code「无→有」
那一刻拉一次桌宠，之后再也不管桌宠死活。踩过一次非常真实的坑——某次桌宠进程没了，
而 MiniMax Code 一直开着，哨兵于是认为「一切正常」，**从此再也没拉过，桌面上空了
一整天**，只能靠关掉再打开 MiniMax Code 才能恢复。

现在改成**状态驱动**：哨兵每一轮都问「应用在吗？桌宠在吗？」，应用在而桌宠不在，
就拉。两个探针任何一个说「在」都算数（刚拉起的宽限期 / 桌宠的单实例锁 / 自己那个
子进程），避免重复拉起。

**但这套设计有个明确的盲区，必须知道：两个进程在同一瞬间一起没了，就没人拉了。**
互相看门的前提是「至少还活着一个」。登录启动项只在**登录那一刻**跑一次，所以如果
哨兵和桌宠一起被杀（手动清理、别的工具、任务管理器批量结束、或注销），桌面会一直
空着，直到你重新登录或自己拉一次。

这个盲区现在由一个 **Windows 计划任务**兜底（见下一节）。

### 计划任务兜底：每 5 分钟确认「还有人活着」

```bat
python autostart.py keepalive on     :: 建任务
python autostart.py keepalive status  :: 看状态
python autostart.py keepalive off     :: 删任务
```

任务名 `MiniMaxPetKeepAlive`，每 5 分钟跑一次：

```
pythonw.exe "...\pet_watcher.py" --ensure
```

`--ensure` 是**幂等**的，逻辑只有三步：

| 情况 | 动作 |
|---|---|
| 处于暂停期（你手动退出过桌宠） | **什么都不做** ← 关键 |
| 哨兵还在跑 | 什么都不做 |
| 哨兵不在了 | 把哨兵拉起来（哨兵自己会去管桌宠） |

**为什么不是 `--resume`**：`--resume` 会清掉「用户主动退出桌宠」的暂停标记。
定时任务每 5 分钟清一次的话，你手动关掉的桌宠 5 分钟后自己就回来了——手动关闭
必须真的是关闭。所以计划任务用的是 `--ensure`，它尊重暂停。

实测（真把两个进程一起杀掉）：

```
08:53:58 ensure：哨兵不在，把哨兵拉起来
08:53:58 已反拉待命哨兵 pid=88400
08:53:58 待命哨兵启动 pid=88400
08:53:58 已拉起桌宠 pid=25272
```

加上暂停标记再杀一次：

```
08:54:28 ensure：处于暂停期（用户手动退出过桌宠），不拉起
08:54:33 ensure：处于暂停期（用户手动退出过桌宠），不拉起
```

桌宠没有回来——**手动关闭被尊重**。

任务本身用 `pythonw`（不弹黑框）、`LogonType=InteractiveToken`（**必须**跑在你自己的
交互会话里，否则它拉起的桌宠虽然是 GUI 进程，却不在你的桌面上）、`IgnoreNew`
（不会堆实例）、`StartWhenAvailable`（错过的会补跑）。

> 这个任务**不碰 MiniMax Code 任何东西**，只是保证「本项目的哨兵进程存在」。
> 撤销就是 `python autostart.py keepalive off`。

### `status` 曾经骗人：把别的桌宠当成自己的

排查「桌宠怎么不见了」时踩到的坑，值得单独记一笔，因为它会**把你带偏**。

`_cmdlines()` 以前返回的是**把全部 pythonw 命令行拼成的一整块文本**，然后
`"pet_watcher.py" in cl` 做子串判断。本机同时装着三个桌宠，其中另一个项目的路径
恰好含有这个子串，于是：

```
别的项目的同名哨兵   旧逻辑：命中 ❌   新逻辑：不认 ✅
本项目哨兵           旧逻辑：命中     新逻辑：认   ✅
```

`autostart.py status` 于是一律报「哨兵在跑：是 ✓」，**而实际上早就没在跑了** ——
排查时会因此以为桌宠还活着，去查完全错误的方向。

现在 `_cmdlines()` 返回**列表**，判定要求命令行**同时**命中脚本名和项目目录名
（`minimaxpet`）；桌宠的端口探测也改成先 `GET /` 并核对正文里的 `MiniMax Pet ok`，
而不是「8766 端口开着就算它在跑」。

> 同机器上跑多只桌宠时还有一点：它们的单实例锁、位置状态都是各自独立的，互不干扰，
> 但**别用「进程名/脚本名」去判断谁是谁**，一定要认目录。


「桌宠在不在」不只看「是不是我拉起来的那个子进程」，还看桌宠自己的
`%TEMP%\minimax-pet.lock`：哨兵重启时如果桌宠还活着（用户手动开的、或刚被反向
看门拉起来的），只认子进程就会不停空拉副本——每个副本抢不到单实例锁、秒退、再拉。

## 大小：为什么拔掉显示器它就变了

**右键点团子 → 「桌宠大小」** 可以选 **小 / 较小 / 标准 / 较大 / 大**，选择记在
`pet_state.json` 的 `size_level` 里，重启后保持。托盘菜单里也有一份。
子菜单最后还有「立即按当前屏幕校正」和「显示物理尺寸信息」。

| 档位 | 逻辑窗口 | 屏幕上的实际大小 |
|---|---|---|
| 小 0.75 | 38×49 | **76×98** |
| 较小 0.9 | 46×58 | **92×116** |
| 标准 1.0 | 51×64 | **102×128** |
| 较大 1.15 | 59×74 | **118×148** |
| 大 1.35 | 69×86 | **138×172** |

（以上是 200% 缩放屏上的实测值。逻辑尺寸随缩放变，**物理尺寸恒定**。）

### 为什么以前会忽大忽小

原来所有几何都是**逻辑像素**，而 Qt 渲染时会按所在屏幕的 DPI 再放大一次：

```
物理大小 = 逻辑大小 × 实际缩放
```

于是同一份 `102×129` 的逻辑尺寸：

- 插着 100% 缩放的外接显示器 → 屏幕上是 **102×129**，刚好好
- 只剩 200% 缩放的笔记本内屏 → 屏幕上是 **204×258**，整整大了一倍

现在改成**锚定物理像素**：`逻辑 = 物理 ÷ 实际缩放`。一除一乘抵消，插拔显示器、
改系统缩放，**屏幕上的实际大小都不变**。插拔时 Qt 会抛
`screenAdded / screenRemoved / primaryScreenChanged`，桌宠收到就重新量一次。

### 缩放比例要实测，不信 Qt

`screen.devicePixelRatio()` 通常是对的，但不保证在所有组合下都对（多屏混合缩放、
DPI 虚拟化、驱动默认值都可能让它和窗口实际表现对不上）。所以窗口出来之后用
`GetWindowRect` 量一次真实比例，对不上就按实测重算——**不信任任何单一来源**。

量的时候要量**高度**而不是宽度：`_fit_width()` 会按状态胶囊文字动态改宽度
（「待命」→「19 步 · 02:34」），用宽度量会被文字长度污染。

### 排查这类问题的两个陷阱

1. **别用 DPI-unaware 的进程去量窗口大小。** PowerShell 默认就是 DPI-unaware，
   它拿到的 `GetWindowRect` / `SystemInformation.VirtualScreen` 全是**虚拟化**后的
   坐标：本机真实屏幕是 2560×1600，它却报 1920×1080，量出来的窗口尺寸会小 1.5 倍
   （真实 102×128 被报成 68×85）。一度据此以为 Qt 的 DPR 是错的，其实是尺子坏了。
   量之前先 `SetProcessDpiAwarenessContext(-4)`。
2. **别用 PowerShell 改 `pet_state.json`。** `Set-Content -Encoding UTF8` 在
   PS 5.1 下会写 UTF-8 BOM，`json.load` 直接抛 `Unexpected UTF-8 BOM`。现在
   `load_state()` 改用 `utf-8-sig` 读取并且**会记日志**，不会再静默丢状态。

### 几个容易踩的点

- **哨兵不 import PyQt5**。它只 import `ctypes`，用 `CreateToolhelp32Snapshot` 数进程。
  这样常驻开销才压得住，也避免和桌宠抢 GIL。
- **哨兵有独立的日志 `watcher.log`**。两个进程同时写 `pet.log` 会互相干扰 512KB 清空逻辑。
- **哨兵主循环必须整体包 `try/except`**（`_guarded_tick`）。哨兵是 pythonw 起的，
  **没有 stderr**：任何未捕获异常都会让它悄无声息地消失，而且 Windows 事件日志里
  连 Application Error 都不会留一条，事后完全查不出线索。现在异常会被吃掉 + 写
  traceback 进 `watcher.log`，外加 `faulthandler` 兜底段错误，外加**每 10 分钟一条心跳**。
- **`PROCESSENTRY32W` 必须定义在模块级，不能写在函数里**。写在函数内部的话，每次调用
  都新建一个类对象，`argtypes` 里绑定的 `POINTER(_PE32)` 只认第一次那个类，第二次
  扫描起 ctypes 就抛 `ArgumentError`。而 `app_pids()` 会把异常吞掉返回空集，
  `app_running()` 于是永远返回 `False` —— 桌宠误以为应用关闭了，先隐藏自己，
  几秒后自杀。**实测表现就是「桌宠起来 4 秒就没了」，且毫无日志。**
- **「扫描失败」绝不能等同于「应用没开」**。`app_pids()` 扫不到任何进程时现在会
  抛出去，让 `app_running()` 的「探测失败=按存活处理」兜底能生效。
- **`CreateToolhelp32Snapshot` 必须声明 `restype`**。不声明时 ctypes 按 `c_int` 返回
  HANDLE，64 位下高位被截断，再把这个被截断的值喂给 `CloseHandle`，关掉的就不是
  那个快照句柄了。
- **哨兵的边沿基准要初始化成「现在的真实状态」**，不能是 `False`。否则哨兵每次重启、
  在应用已经开着的情况下，都会误判成「应用刚打开」，把用户「暂时别拉桌宠」的标记
  一起清掉。
- **哨兵有单实例锁**（`.watcher.lock`）。`autostart.py status` 里的查询用的是
  `lock_held_by_other()` 而不是 `acquire_lock()`——后者会**真的把锁抢过来**，
  正在跑的哨兵下次续租就断了。

### 曾经让桌面空了一整天的那两个坑（都跟 QLockFile 有关）

单实例锁 `%TEMP%\minimax-pet.lock` 是 Qt 的 `QLockFile` 管的。它有两个独立行为：
**①** 用 `LockFileEx` 锁住整个文件；**②** 加锁前先读文件里的 `pid + hostname`，
判断写锁的那个进程是不是还活着。

坑一：**任何代码都别往这个文件里写东西。**
桌宠干净退出时 Qt 会把锁文件**清空**。哨兵的存活探针当时用 `"a+b"` 打开它，
看到文件是空的就顺手写了 `b"0"` —— 文件内容从此变成 `0`，`QLockFile` 读不出合法
锁记录，**永久拒绝加锁**（`error() == 1` LockFailedError），而且 `setStaleLockTime(0)`
又关掉了 Qt 自己的过期清理，于是**再也起不来**。

实测后果：桌宠每 20 秒被拉起一次、每次活 1 秒、返回码 0，`pet.log` 里一行都没有
（那次抢锁失败只有 `print()`，pythonw 下谁也看不见）。哨兵一天累计拉了 **2158 次**，
桌面全程空白。现在 `pet_running()` 改成 `"r+b"` 只读打开，且**连续 2 次**
「拉起即被单实例锁挡回、又确实没有桌宠在跑」就判定锁文件坏了，`break_pet_lock()`
删掉它再来一次。

坑二：**宽限期不能掩盖「进程已经退了」。**
「刚拉起，给桌宠几秒抢锁」的宽限期（`SPAWN_GRACE_SEC`）只在**子进程还活着**时才有
意义。子进程 1 秒就退了，说明这次拉起已经结束，这时还拿宽限期当「桌宠在跑」，
就会走进「已有桌宠在运行，跳过」的死路——锁自愈逻辑永远等不到触发，表现和坑一
一模一样。

> 这两条现在都有回归探针守着：`_probe_watcher.py` 里
> 「300 次调用后文件大小/mtime 完全不变」「子进程已死 → 宽限期不再把它当成桌宠在跑」
> 「第 2 次失败 → 立刻清锁」三项。
- **`app_seen` 必须在构造时就探测**。桌宠通常是被哨兵在检测到应用打开后拉起来的，
  这时起始状态是 `True`；如果用户手动双击 `MiniMaxPet.bat` 而应用没开，起始必须是
  `False`，否则「连续两次没检测到才判关闭」那个分支永远不触发，桌宠会一直赖着。
- **`--always-show`** 是给手动调试用的，强制启动就显示不等应用。

`watcher.log` 和 `pet.log` 里的 `[lifecycle]` 行可以对照实际行为。

### 登录待命（开机自动等 MiniMax Code）

```bat
python autostart.py on       :: 开启
python autostart.py status   :: 查看 + 体检（哨兵/桌宠/解释器/MiniMax 是否在跑）
python autostart.py verify   :: 真跑一次 WSH，确认哨兵确实被拉起
python autostart.py off      :: 关闭
python autostart.py keepalive on    :: 建「每 5 分钟确认有人活着」的 Windows 计划任务
python autostart.py keepalive off   :: 删掉它
python autostart.py keepalive status :: 看它

python pet_watcher.py --status   :: 单独看哨兵状态与最近日志
python pet_watcher.py --unpause  :: 撤销「这次先别拉桌宠」（托盘点过退出桌宠时用）
```

它只写**一个文件**：

```
%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\MiniMaxPet.vbs
```

内容是一行「用 pythonw 无窗口跑本项目的 `pet_watcher.py`」——**注意是哨兵，不是桌宠**：

```vbscript
CreateObject("WScript.Shell").Run """C:\...\pythonw.exe"" ""C:\...\pet_watcher.py""", 0, False
```

里面**写死了解释器的绝对路径**——Startup 项是登录时由 WSH 执行的，那时的 PATH 未必带
Python，只写 `pythonw` 会静默失败。`status` 会在 Python 搬家后明确告诉你失效了。

⚠️ 这是本项目**唯一**会写到目录之外的动作。`off` 就是删掉那一个 VBS。不碰注册表、
不碰 MiniMax Code 的任何配置、不装钩子。

单实例锁有两个，两层各管各的：

| 进程 | 锁 | 作用 |
|---|---|---|
| 哨兵 | `.watcher.lock`（`msvcrt.locking`） | 防止起两个哨兵重复拉起桌宠 |
| 桌宠 | `%TEMP%\minimax-pet.lock`（`QLockFile`） | 防止手动双击和哨兵拉起打架。哨兵也拿它当「桌宠还在不在」的探针 |

| `--selftest-live` | 自检时**读取真实会话**，额外产出 `L0-live-<状态>.png`、`L0-live-state.txt` 和 `live-demo-*.png`（真实会话优先级更高，演示帧会被它盖住，所以另起文件名，不污染上面那套确定可复现的 `1-…7-`） |
| `--port 8766` | 本地事件入口端口（默认 8766，被占用会自动往后顺延，最多试 10 个） |
| `--no-follow` | 启动即**关掉**跟随（不再随 MiniMax Code 显隐，只听手动开关）。默认开 |
| `--exit-with-app` | 启动即开启「MiniMax **完全退出**时一并退出桌宠」（跟进程，不是跟窗口） |
| `--no-server` | 不开启本地 HTTP 事件入口 |
| `--resume` | 手动重新启用：先清掉「用户退出桌宠」的暂停标记再启动。`MiniMaxPet.bat` 传的就是它，**双击它就能把手动关掉的桌宠拉回来** |
| `--ensure` | 幂等的「确保有人活着」：暂停中就什么都不做，否则把哨兵拉起来。**Windows 计划任务每 5 分钟跑它** |
| `--probe-activate` | 不启动桌宠，只把「召唤 MiniMax Code」链路跑一遍：进程、祖先链、exe 路径、每个窗口活不活、最终走了哪个分支，然后退出 |

`--port` 的 HTTP 入口是给**演示和外部自定义推送**用的扩展点（不需要就加 `--no-server` 关掉）：

```bat
curl -X POST http://127.0.0.1:8766/event ^
     -H "Content-Type: application/json; charset=utf-8" ^
     -d "{\"state\":\"executing\",\"task\":\"跑回归测试\",\"tool\":\"Bash\",\"project\":\"demo\"}"
```

- `state` 取值：`idle` / `thinking` / `executing` / `waiting` / `done` / `error`
- `task` / `tool` / `project` 可选，会出现在卡片上；`task` 超过 90 字自动截断
- `state` 缺失或不合法时退化为「演示一轮」，方便随手 curl 一下看效果
- `GET http://127.0.0.1:8766/` 返回一行存活状态，用来探端口

## 主视觉

团子本体直接取自 MiniMax Code 安装目录里的 `icon.icns`（`resources/resources/icon.icns`），
**不是手绘近似**。表情是运行时叠加的：眨眼、视线跟随、微笑、思考冒 M 气泡、等你确认橙色脉冲
叹号、出错红色叹号、完成弯月眼 + 四角闪光。

状态图标（✓ ⏸ ✕ ▶）全部是 QPainter 矢量绘制，不依赖字体符号字形——因为 Qt 样式表的
`font-family` 不做逐字形回退，直接写符号会掉成豆腐块。字体栈见 `minimax_pet.py` 的
`FONT_FAMILIES`。

### 抠图为什么不能用「颜色阈值」

官方 `icon.icns` 里吉祥物是**压在白色圆角底板上**的（不透明像素里 53% 是近白），所以必须抠底。
但不能用「离白够近就是底板」这种硬判，原因有两个：

1. 边缘那一两像素是**主体和底板混出来的浅蓝**（`(223,239,255)`，`b-r=32`）。按
   `(b-r) > 10` 判会把它整片留成**不透明的近白色**——放到浅色桌面上就是用户看到的
   一圈白噪点；
2. 输出里半透明像素数为 **0**，边缘是硬的，缩放后必然锯齿。

现在 `key_out()` 走「粗掩码 + 局部 matting」三步：

| 步骤 | 做法 |
|---|---|
| ① 粗掩码 | 分数 `(max-min) + (255-luma)×1.6` 低于 70 的算白底候选，再从裁切框四边 flood |
| ② 传播 | 取粗掩码两侧各 2px 做过渡带，把**纯主体色**向带内扩散 7 轮 |
| ③ 解算 | 逐像素解 `obs = a·m + (1-a)·255` 得到真实覆盖度 `a`，再反解主体色 `m` |

① 用「色度 + 亮度」而不是「到白的距离」，是因为吉祥物底部那圈浅青 `(185,251,255)`
到白只有 70，**且直接贴着底板**——按距离判 flood 会灌进去把脚啃掉。flood 只看连通性，
主体内部的浅色高光被身体围住，不会被误伤。

只有第 ① 步是近似的；第 ③ 步是逐像素精确解，所以过渡带落在哪里都不影响边缘质量。
实测产物：半透明边缘 5135 px，**不透明近白像素 0**，缩到实际显示尺寸 101×105 后仍是 **0**。
（`build_assets.py` 每次构建都会自检这一项。）

### 立体感怎么来的

在官方像素之上叠了三层，**故意不加顶部轮廓光**：

| 层 | 参数 | 作用 |
|---|---|---|
| 落地阴影 | 垂直密度梯度，下浓上淡 | 原来是对称模糊 = 一圈均匀光晕，像描边；加梯度后才是「压在桌面上」 |
| 底部暗部 | 下边界 6px，压深蓝 | 给身体体积，不是平贴纸 |
| 外发光 | 品牌蓝，`opacity=26/255` | 把主体从背景托起来 |

> 顶部轮廓光试过（沿上边界打亮）。确实有受光的错觉，但在 596px 图上是一条 2~3px
> 浅色带，缩到实际显示的 101px 仍然看得见——落在浅色桌面上就是一圈白边，
> 正好是这次要消灭的东西，所以去掉了。

## 改大小 / 改字号

有两个**互相独立**的旋钮，都在 `minimax_pet.py` 顶部：

```python
SIZE_RATIO = 0.8     # 几何：团子、胶囊、卡片、动画幅度一起缩
FONT_SCALE = 1.2     # 字号：只管字，不跟几何缩
```

分开是有原因的：**文字有可读性下限**。桌子缩小只该影响能放几个字，不该把 12px 的中文
压到 10px 以下——那样看着费劲。所以两者分开，想调哪边动哪边。

| 旋钮 | 影响 | 当前值 |
|---|---|---|
| `SIZE_RATIO` | 团子本体、状态胶囊、任务卡片尺寸、表情动画幅度 | 0.8（设计稿 128×160 → 102×129） |
| `FONT_SCALE` | 卡片标题/状态/元信息、状态胶囊的字号 | 1.2（标题 12→14px，状态 11→13px，元信息 10→12px） |

任务卡片的设计稿尺寸 322 × 66 → 实际 258 × 53。卡片里两行文字的行高是**由字体度量算出**
的，不是写死的，所以放大 `FONT_SCALE` 不会被裁掉；如果嫌挤，把 `CARD_H` 调大即可。

`--selftest-scale N` 是「按 N 倍渲染当前实际尺寸」用于肉眼查细节，不改这两个常数。

改完重启桌宠即可生效（托盘右键 → 退出，再双击 `MiniMaxPet.bat`）。
